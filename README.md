# Аукцион коллекционных предметов

Это REST API для аукциона. Пользователь может выставить свой коллекционный предмет на торги, другие
пользователи делают ставки, а когда торги заканчиваются, победитель получает предмет.
Написано на Java 17 и Spring Boot, данные хранятся в базе MySQL.

## Из чего состоит приложение

| Что | Адрес | Что хранится |
|---|---|---|
| Пользователь | `/api/users` | имя и e-mail (e-mail не повторяется) |
| Коллекционный предмет | `/api/collectible-items` | описание, владелец, состояние |
| Аукционный лот | `/api/auction-lots` | какой предмет продаётся, стартовая цена, шаг ставки, когда начало и конец, статус |
| Ставка | `/api/bids` | на какой лот, кто поставил, сумма, время (его ставит сервер) |
| Сделка | `/api/auction-deals` | по какому лоту, какая ставка выиграла, сумма, передан ли предмет |

Как всё связано:

- у предмета есть владелец (пользователь);
- лот создаётся для одного предмета;
- ставка относится к одному лоту и сделана одним пользователем;
- по лоту может быть одна сделка, и в ней указана выигравшая ставка.

Статусы лота: `DRAFT` (черновик), `ACTIVE` (идут торги), `FINISHED` (торги закончились),
`CANCELLED` (отменён). Статусы сделки: `PENDING` (ждёт передачи), `TRANSFERRED` (предмет передан),
`CANCELLED` (отменена).

## Что проверяет сама база данных

Правила записаны в `db/1_schema.sql`, поэтому они работают, даже если ошибиться в коде:

- нельзя создать запись со ссылкой на то, чего нет (например, ставку на несуществующий лот);
- если удалить пользователя, предмет, лот или ставку, то всё, что с ними связано, удаляется тоже,
  битых ссылок не остаётся;
- цена, шаг и сумма ставки больше нуля, а конец торгов позже начала;
- статусы могут быть только из списка;
- e-mail у пользователей не повторяется;
- один предмет нельзя выставить на двое торгов одновременно;
- по одному лоту не больше одной сделки;
- выигравшая ставка должна быть именно с этого лота, а сумма сделки равна сумме этой ставки.

## Бизнес-операции

Это действия, которые меняют сразу несколько сущностей. Результат зависит от того, в каком состоянии
сейчас данные. Если действие в этом состоянии нельзя делать, вернётся ошибка `409`, и ничего не изменится.
Каждая операция выполняется целиком или не выполняется совсем.

1. **Выставить предмет на торги**: `POST /api/collectible-items/{id}/list-for-auction`.
   Нельзя, если предмет уже торгуется или продан и ждёт передачи. Время окончания должно быть в будущем,
   а начало торгов сервер ставит сам.

2. **Сделать ставку**: `POST /api/auction-lots/{id}/place-bid`.
   Можно, только пока лот активен и время торгов не вышло. Владелец не может ставить на свой предмет.
   Тот, кто сейчас лидирует, не может перебивать сам себя. Ставка должна быть не меньше стартовой цены
   или (если ставки уже есть) не меньше лидирующей ставки плюс шаг.

3. **Завершить торги**: `POST /api/auction-lots/{id}/close`.
   Только для активного лота. Если ставки были, выигрывает самая большая: создаётся сделка (`PENDING`),
   лот становится `FINISHED`. Если ставок не было, лот становится `CANCELLED`, сделки нет.

4. **Подтвердить передачу предмета**: `POST /api/auction-deals/{id}/confirm-transfer`.
   Только для сделки `PENDING`. Владельцем предмета становится победитель, сделка получает `TRANSFERRED`.

5. **Отменить сделку**: `POST /api/auction-deals/{id}/cancel`.
   Только для сделки `PENDING`. Лот становится `CANCELLED`, предмет остаётся у прежнего владельца,
   и его можно выставить на торги заново.

Обычный `POST /api/bids` работает по тем же правилам, что и «Сделать ставку», так что обойти правила нельзя.

## Обычные операции (CRUD)

Для каждой сущности есть пять запросов: список (`GET /api/...`), один объект (`GET /api/.../{id}`),
создание (`POST`), изменение (`PATCH /{id}`), удаление (`DELETE /{id}`).
Коды ответов: чтение `200`, создание `201`, изменение `200`, удаление `204`.
Ошибки: `400` (неправильные данные), `404` (не найдено), `409` (нарушено правило или ограничение базы).
Текущее время всегда ставит сервер, из запросов оно не берётся.

## Как запустить

Нужны Java 17 или новее, Maven и MySQL 8. Саму базу и пользователя для неё создаю заранее (у меня их выдал
хостинг). Приложение работает под пользователем с ограниченными правами: только `SELECT`, `INSERT`, `UPDATE`
и `DELETE` на эту базу. Создавать, менять и удалять таблицы он не может, поэтому таблицы в шаге 1 создаю
отдельно, под владельцем базы.

1. Один раз создаю таблицы. Подключаюсь к своей базе в любой программе для MySQL (например, в IntelliJ IDEA
   или phpMyAdmin) и выполняю по порядку два файла из папки `db`:

   | Файл | Что делает |
   |---|---|
   | `1_schema.sql` | создаёт таблицы, связи и ограничения |
   | `2_seed.sql` | добавляет тестовые данные |

   Каждый файл выполняется один раз. Данные в базе сохраняются между запусками приложения, сами они
   не стираются и не пересоздаются.

2. Создаю в корне проекта файл `.env` (он не попадает в git) и пишу в него настройки подключения:

   ```
   DB_URL=jdbc:mysql://хост:3306/имя_базы?characterEncoding=UTF-8
   DB_USER=пользователь
   DB_PASSWORD=пароль
   ```

   Эти же значения можно задать обычными переменными окружения.

3. Запускаю приложение:

   ```bash
   mvn spring-boot:run
   ```

## Тестовые данные

После `2_seed.sql` в базе есть 4 пользователя, 4 предмета, один лот, по которому идут торги (с двумя
ставками), и один завершённый лот со сделкой, которая ждёт передачи. Так можно сразу пробовать операции.

## Коллекция запросов

Файл `requests.http` открывается в IntelliJ IDEA. Запросы идут по порядку сверху вниз. Сначала CRUD по
каждой сущности (и проверка, что при удалении связанные данные тоже удаляются). Потом сценарий: выставили
предмет, сделали ставки, завершили торги, передали предмет, выставили его снова, отменили сделку.
Номера созданных объектов запоминаются и подставляются в следующие запросы, а ответы проверяются
автоматически. Коллекция создаёт свои данные, поэтому не зависит от тестовых записей в базе.

## Из каких папок состоит проект

```
src/main/java/org/example
├── controller   принимают запросы (CRUD и бизнес-операции)
├── service      вся логика; бизнес-операции в AuctionService
├── repository   работа с базой данных
├── model        сущности (таблицы в виде классов)
├── dto          данные, которые приходят в запросах
└── exception    ошибки и коды ответов на них
db               SQL для базы: таблицы и тестовые данные
```
